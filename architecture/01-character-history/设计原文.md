**可以。这个设计适合续写：把人物建成对象，把会变化的属性建成有原文依据的历史记录，再计算“截至某章的人物状态”。**

你说的“链表”可以理解为一条变化历史。实际实现用按时间排序的列表或数据库记录即可，不必真的实现指针链表。

人物对象可以这样组织：

```python
class Character:
    id: str
    names: list                 # 本名、别名、化名
    identity_history: list      # 身份变化
    relationship_history: dict  # 对其他人物的关系变化
    attitude_history: dict      # 对其他人物的态度变化
    ability_history: dict       # 功法、技能与掌握情况
    outfit_history: list        # 穿着变化
    inventory_history: list     # 持有、借出、丢失的物品
    condition_history: list     # 伤势、疲劳、境界等
    knowledge_history: list     # 知道、相信、误解了什么
    goal_history: list          # 当前想完成什么
```

这是设计示意，尚未实现。

**关键是每条变化记录都不能只有“新值”。**至少应包含：

```text
属性：对角色乙的信任
变化：戒备 → 愿意暂时合作
发生时间：某次事件之后
原文出现位置：第90章，片段ID……
依据：具体行动或对话
判断类型：明确表述 / 行为推断 / 角色自述
有效范围：本次合作，长期状态尚不明确
```

这里用的是虚构示例，不是在断言《妖女看招》的剧情。

你提到的几类属性，需要稍微区别处理：

| 属性 | 适合怎样记录 | 容易误判的地方 |
| --- | --- | --- |
| **好感度** | 喜爱、信任、恐惧、敌意、依赖等分别记录 | 一个人可能喜欢对方，同时不信任对方；一个数字装不下 |
| **人物关系** | 有方向、有阶段的关系，如“甲视乙为老师” | 甲认可的关系，乙未必认可；公开身份与真实关系可能不同 |
| **功法** | 学到、练习、掌握、施展、受限、失去、恢复 | 施展一次可能靠借力，不代表永久掌握 |
| **穿着** | 在具体场景中的穿戴、破损、脱下、更换 | 第10章穿红衣，不能自动延续到第90章 |
| **性格** | 相对稳定的倾向，以及支持或反驳它的行为 | 一次生气是情绪，未必是性格变化 |
| **知情状态** | 知道什么、从谁得知、相信程度、是否被证伪 | 读者知道的秘密，角色可能不知道 |

对于“好感度”，**先保存文字证据和多维态度最可靠**。若后续模拟需要数值，可以再映射为分数，并标明这是模型估计；原文没有提供分数，就不能把“好感度73”写成事实。

还有一个特别重要的设计：**同时记录故事时间和披露章节。**

例如，第100章通过回忆揭示了第20章之前发生的一件事：

- 按故事时间查询，它早已发生；
- 按“读到第90章”的视角查询，它尚未披露；
- 某个角色可能一直知道，另一个角色直到第110章才知道。

所以可以提供三种不同的查询：

```python
character.as_of_chapter(90)       # 读者截至90章能确认的状态
character.at_story_time(event)   # 故事中某时点的状态
character.knowledge_at(event)    # 角色当时知道或相信什么
```

**接到我们现有 LightRAG 上，可以这样分工：**

1. LightRAG 找到人物、功法、物品及相关原文。
2. 从可信原文提取“谁的哪个属性，在什么事件中发生变化”。
3. 保存带来源的变化记录；遇到冲突保留双方依据。
4. 按时间和章节条件生成角色卡。
5. 续写后，把新变化写进独立的续写分支，保留原作状态。

这样，**角色卡就能随章节生成，而不必维护一份不断被覆盖的长摘要**。我们下一步最合适的试点是：选两三个主要人物，先做“关系、知情、能力”三条历史，检查它们能否准确还原几个指定章节的状态，再扩展到穿着、物品和全部人物。
